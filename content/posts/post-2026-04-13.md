Business Email Compromise (BEC) is one of the most financially damaging threats organizations face today. Attackers only need access to a mailbox and a few quiet inbox rules. This post walks through a Sigma detection rule I built and contributed to [SigmaHQ](https://github.com/SigmaHQ/sigma/pull/5934) covering six real-world BEC techniques observed in Microsoft 365 Exchange environments.

## The Problem

Once an attacker compromises an M365 account — typically through phishing, credential stuffing, or AiTM — their first move is often persistence and concealment. They create inbox rules that:

- Move security alerts to RSS folders or Junk
- Silently delete emails containing keywords like "hacked" or "phishing"
- Redirect or forward emails to an external attacker-controlled address
- Grant themselves full mailbox access via delegation

These rules run silently in the background. The victim sees nothing. The attacker maintains persistent access even after password resets if the rules aren't cleaned up.

## Detection Strategy

The rule targets Microsoft 365 Exchange audit logs and monitors for six techniques. The core operations are:

- `New-InboxRule` — new rule created via Outlook Web
- `Set-InboxRule` — existing rule modified
- `UpdateInboxRules` — rule created or modified via Outlook desktop client
- `Set-Mailbox` — mailbox forwarding configured
- `Add-MailboxPermission` — mailbox delegation granted

  selection_bec_keywords:

      - 'payroll'

      - 'deposit'
      - 'docusign'
      - 'WeTransfer'
      - 'postmaster'

  # Technique 5 - Mailbox forwarding to external address
  selection_mailbox_forwarding:
    Operation: 'Set-Mailbox'
    Parameters|contains:
      - 'ForwardingSmtpAddress'
      - 'DeliverToMailboxAndForward'

  # Technique 6 - Full mailbox access delegated
  selection_mailbox_delegate:
    Operation: 'Add-MailboxPermission'
    Parameters|contains: 'FullAccess'

  condition: 1 of selection_*

falsepositives:
  - Users legitimately forwarding mail to personal accounts
  - IT admins configuring mailbox delegation for executives
  - Automated systems creating inbox rules for mail management
  - Help desk or admin workflows granting mailbox access
  - Users organizing mail into archive or junk folders via rules
  - Finance or HR teams with rules filtering payroll or deposit-related emails
  - Internal email redirects between team mailboxes

level: medium

## Technique Breakdown

### Technique 1 — Suspicious folder redirection

Attackers redirect incoming emails to low-visibility folders — RSS Subscriptions, Junk Email, Deleted Items, or Conversation History — so the victim doesn't see security alerts or responses to fraudulent emails the attacker sent on their behalf.

### Technique 2 — Silent message deletion

Rules configured with `DeleteMessage: True` silently drop emails matching attacker-defined criteria. Common keywords targeted include "hacked", "phishing", "spam", and "virus" — anything that might tip off the victim.

### Technique 3 — External redirect and forwarding

`RedirectTo` drops the original copy entirely and sends to the attacker. `ForwardTo` keeps a copy in the victim's inbox while also sending to the attacker. Both are used in BEC. Both are detected here.

### Technique 4 — BEC keyword filtering

Attackers create rules that filter emails containing financial keywords — invoice, payment, wire transfer, payroll — and route them to attacker-controlled addresses or hidden folders for monitoring and fraud execution.

### Technique 5 — Mailbox forwarding via Set-Mailbox

Unlike inbox rules, `Set-Mailbox` with `ForwardingSmtpAddress` configures forwarding at the mailbox level. This persists independently of inbox rules and survives rule cleanup. Often missed in investigations focused only on `New-InboxRule`.

### Technique 6 — Mailbox delegation

`Add-MailboxPermission` with `FullAccess` grants an attacker persistent access to read, send, and manage the victim's mailbox. Maps to [T1098.002](https://attack.mitre.org/techniques/T1098/002/) and [DET0373](https://attack.mitre.org/detectionstrategies/DET0373/).

## Triage Guidance

When this rule fires:

1. Identify the operation that triggered it and the user account involved
2. Pull the full `Parameters` field to inspect the rule configuration
3. Check the source IP of the rule creation event — is it consistent with the user's normal login geography and ISP?
4. Review 30 days of login activity for that account for anomalies
5. Check for additional inbox rules on the account using `Get-InboxRule -Mailbox <user> -IncludeHidden`
6. If delegation was granted, check `Add-MailboxPermission` events for other accounts from the same IP
7. Escalate and begin IR if the user is unaware of the rule

## False Positive Considerations

This rule fires on legitimate activity. At `medium` severity the expectation is analyst review, not automated response. Common benign triggers:

- IT admins granting delegation to executive assistants
- Users setting up personal forwarding to Gmail or Outlook.com
- Finance teams filtering invoice-related mail into folders
- Automated provisioning scripts that configure mailbox settings

Tune by building an allowlist of known-good user/operation pairs in your SIEM after observing baseline behavior for 2-4 weeks.
