DNS is one of the most consistently abused protocols in adversary operations. It is universally permitted outbound, rarely inspected at depth, and generates enough baseline noise that malicious queries frequently go unnoticed. This post covers a Sigma detection rule designed to surface three distinct DNS-based threat patterns: queries to known data exfiltration services, queries resolving to high-risk or abused top-level domains, and subdomain patterns consistent with DNS tunneling.

## The Problem

DNS-based exfiltration and command-and-control activity falls into three operational patterns that each require a different detection approach.

**File sharing and paste service abuse** is the most direct. Adversaries and malware resolve domains like `transfer.sh`, `mega.nz`, `pastebin.com`, or `privatebin.net` to stage stolen data or retrieve second-stage payloads. These services are legitimate, which is why they are effective — they blend into normal web traffic. Detection requires maintaining a curated list of these domains and alerting on any DNS resolution against them.

**Abused TLDs** represent a softer signal. TLDs such as `.tk`, `.ml`, `.ga`, `.cf`, and `.gq` have historically offered free or anonymous registration, making them disproportionately represented in malicious infrastructure. Newer TLDs like `.zip` and `.mov` — which mirror common file extensions — have been actively weaponized in phishing and payload delivery operations since their introduction. Querying for domains ending in these TLDs, after filtering out known-legitimate namespaces, surfaces anomalous resolution activity that warrants investigation.

**DNS tunneling** encodes data inside DNS queries themselves, typically in the subdomain label. A query like `OS44LjcuNg__-V2luNy1ob21I-SGFycnkgUG90dGVy.badsite.com` carries base64-encoded data in the subdomain. Tools like `dnscat2`, `iodine`, and `dns2tcp` operate on this principle. The subdomain label in a legitimate query is typically short and human-readable. A label exceeding 30 characters composed of base64url characters is a reliable anomaly indicator.

## The Rule

```yaml
title: Suspicious DNS Query to Known Exfil Domain or Uncommon TLD
id: fc103796-cd46-4569-a962-fd14850c50f7
status: experimental
description: |
  Detects DNS requests to known data exfiltration domains or
  domains with uncommon TLDs indicative of C2 or exfiltration
  activity.
references:
  - https://unit42.paloaltonetworks.com/dns-tunneling-how-dns-can-be-abused-by-malicious-actors/
  - https://attack.mitre.org/techniques/T1048/003/
  - https://attack.mitre.org/techniques/T1071/004/
author: Tashnim Asgar (lanceterminal)
date: 2026/04/16
tags:
  - attack.exfiltration
  - attack.t1048
  - attack.command-and-control
  - attack.t1071.004
logsource:
  category: dns
detection:
  selection_exfil_domains:
    dns.question.name|contains:
      - 'ghostbin.com'
      - 'pastebin.com'
      - '0bin.net'
      - 'privatebin.net'
      - 'mega.nz'
      - 'wetransfer.com'
      - 'sendspace.com'
      - 'anonfiles.com'
      - 'file.io'
      - 'mediafire.com'
      - 'transfer.sh'
      - 'gofile.io'
      - 'pixeldrain.com'
      - 'ufile.io'
      - 'temp.sh'
      - 'bashupload.com'
      - 'paste.ee'
      - 'hastebin.com'
      - 'dpaste.com'
  selection_suspicious_tlds:
    dns.question.name|endswith:
      - '.xyz'
      - '.top'
      - '.tk'
      - '.ml'
      - '.ga'
      - '.cf'
      - '.gq'
      - '.pw'
      - '.su'
      - '.to'
      - '.bazar'
      - '.bit'
      - '.coin'
      - '.zip'
      - '.mov'
      - '.onion'
  filter_common_tlds:
    dns.question.name|endswith:
      - '.com'
      - '.net'
      - '.io'
      - '.co'
      - '.org'
      - '.gov'
      - '.edu'
      - '.uk'
      - '.ca'
      - '.au'
      - '.de'
      - '.fr'
      - '.jp'
      - '.us'
      - '.int'
      - '.mil'
  filter_legitimate_subdomains:
    dns.question.name|re: '^[a-zA-Z0-9-]{1,63}\.[a-zA-Z0-9-]{1,63}\.[a-z]{2,}$'
  selection_suspicious_subdomains:
    dns.question.name|re: '^[A-Za-z0-9+/=_-]{30,}\.'
  condition: selection_exfil_domains or (selection_suspicious_tlds and not filter_common_tlds) or (selection_suspicious_subdomains and not filter_legitimate_subdomains)
falsepositives:
  - Legitimate use of file sharing services
  - Security researchers
  - Software using uncommon TLDs (e.g. .dev, .app)
  - CDN and analytics platforms with long subdomain strings
level: high
fields:
  - dns.question.name
  - dns.resolved_ip
  - process.name
  - process.pid
  - process.command_line
  - process.parent.name
  - host.name
  - user.name
```

The `contains` modifier is intentional over `endswith`. It catches subdomains — `dl.mega.nz`, `api.transfer.sh` — that an `endswith` check on the apex domain would miss. Any DNS resolution against this list in a corporate environment is worth investigating. Legitimate business use of these services should be documented and handled via environment-specific suppression, not by relaxing the rule.

### Branch 2 — Suspicious TLD with Common TLD Filter

```yaml
selection_suspicious_tlds:
  dns.question.name|endswith:
    - '.tk'
    - '.ml'
    - '.zip'
    - '.onion'
    ...
filter_common_tlds:
  dns.question.name|endswith:
    - '.com'
    - '.net'
    - '.org'
    ...
condition: ... (selection_suspicious_tlds and not filter_common_tlds)
```

A naive TLD blocklist fires on everything in that namespace including legitimate traffic. The `filter_common_tlds` block inverts this — it passes only queries that match a suspicious TLD and do not also match a common legitimate TLD. This is particularly relevant for multi-label domains where the query might terminate in `.co.uk` or similar constructs that could otherwise produce false positives.

The `.zip` and `.mov` TLDs warrant specific mention. These were introduced by Google in 2023 and immediately attracted abuse due to their visual similarity to file extensions. A URL like `invoice.zip` renders as a plausible filename in many contexts while resolving as a live domain. Their inclusion here is deliberate.

### Branch 3 — High-Entropy Subdomain (DNS Tunneling)

```yaml
selection_suspicious_subdomains:
  dns.question.name|re: '^[A-Za-z0-9+/=_-]{30,}\.'
filter_legitimate_subdomains:
  dns.question.name|re: '^[a-zA-Z0-9-]{1,63}\.[a-zA-Z0-9-]{1,63}\.[a-z]{2,}$'
condition: ... (selection_suspicious_subdomains and not filter_legitimate_subdomains)
```

The regex `^[A-Za-z0-9+/=_-]{30,}\.` matches any query where the first label is 30 or more characters drawn from the base64url alphabet — the character set used by tunneling tools to encode data. The `filter_legitimate_subdomains` exclusion suppresses standard two-label FQDNs that happen to have longer hostnames, reducing noise from CDN and analytics platforms.

The 30-character threshold is a starting point. In practice, baseline your environment's DNS query length distribution before deploying. Most legitimate subdomains resolve well under 20 characters. Anything above 30 with base64 character composition is an outlier worth investigating.

## Deployment Considerations

**Log source requirements** — This rule operates on `category: dns` in Sigma's logsource taxonomy. In practice this maps to network-level DNS logs from a resolver, DNS forwarder, or NDR platform. Sysmon Event ID 22 (`dns_query` category, `product: windows`) covers endpoint-level DNS but has a narrower field set. Validate your pipeline maps `dns.question.name` correctly before deploying.

**False positive management** — Branch 1 will fire on any employee using a listed service for personal file transfers. Establish a process for documenting legitimate use cases and building environment-specific suppression rules rather than modifying the detection logic. Branch 3 will produce FPs from Akamai, Cloudflare, and similar CDNs with long subdomain tokens — add a `filter_known_cdns` block scoped to your observed CDN patterns.

**Tuning the subdomain threshold** — The 30-character regex threshold should be validated against a week of DNS query logs from your environment before going to production. Adjust upward if CDN noise is significant, or combine with a `dns.question.type: TXT` filter to narrow to the record type most commonly used by tunneling tools.

**Backend compatibility** — The `|re` modifier in Branch 3 is not supported by all Sigma backends. Backends confirmed working include Splunk, Elastic, and Kusto. Datadog's detection rule query format does not currently support regex — deploy Branches 1 and 2 via Sigma conversion and implement Branch 3 natively in your SIEM if using Datadog.
